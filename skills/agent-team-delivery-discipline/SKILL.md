# 多智能体协作交付纪律

适用于「一个人指挥多个 agent 跑长周期数据/代码任务」的场景。核心目标：**让"已完成"这三个字可信**。

这些规则全部来自真实事故，每条都注明它防的是什么。

---

## 一、记录与可追溯

### 1. 预注册登记表**不可原地改**
登记表是**承诺**，不是状态快照。口径变了要**另加一行**（如 `xxx_domainfix`），**保留原行**。
- 判据：登记表要能回答「**第一版用了什么、第二版用了什么**」，不是「现在是多少」。
- 防的是：事后把历史值改成现值 ⇒ 无法复核「当时的结论建立在什么口径上」。

### 2. 活文档**不进 md5 冻结基线**
被团队持续追加的文档（坑表、changelog、阶段汇报）md5 **必然漂**。
- 改冻**「条目标题集合」**（如 `P-001…P-020` 的标题列表）或**条数下限**。
- 字节级 md5 只用于**交付冻结件**：结果表、定稿文档、脚本。
- 防的是：给一个必然变化的量做冻结 ⇒ 基线**天生就是错的** ⇒ 每次核对都产生**假警报**。

### 3. 「补落」必须与「原生」区分
- `run_manifest_posthoc = TRUE` **只用于**「事后给历史产物补写 manifest」。
- **原生跑出来**的产物 ⇒ `FALSE` / 不标。
- 禁用「代码 md5 == 产物 md5」作判据（两者语义不同）。
- 防的是：后人分不清「这份记录是跑的时候写的，还是事后补的」，真伪不分。

### 4. 转发他人的文件，md5 必须在**转发那一刻**重取
不得沿用对方消息里的旧值。
- 防的是：转发的 md5 与实际文件不符 ⇒ 下游核对失败，白跑一轮排查。

### 5. 改动留痕，不抹历史
撤销一个决定时，**删除产物但保留记录**：另存 `.bak.<原因>_<时间戳>`，并在 changelog 写明「曾有过什么、因为什么被撤销」。
- 防的是：下一个读表的人把已撤销的版本当成现状。

---

### 5b. 「待办台账」最常见的退化形态 = **状态列陈旧**

- 台账的用途是"**读待办**"，于是**没人回头改已完成行** ⇒ 已完成项长期挂着 `待执行`，**读者会把已交付的工作重新派一遍**。
  实测：同一份《裁定台账》里 **2 条早已完成**（一条是"按症状反查降权文件"、一条由 team-lead 代做落盘），状态列仍是 `待执行`。
- 对策：① 台账需要**专职更新者**（本项目指定 `data-engineer` 统一更新，执行方也可自行改状态列）；
  ② **每条裁定必须带「责任人 + 状态」两列**，否则无法结案；
  ③ 台账是**多主体共写** ⇒ **改写前先重读并比对 md5（CAS）**，且**只改状态列、不改历史裁定行**（已实测 1 次裸写覆盖竞态）。
- ⚠️ 状态列里写的**数字同样受"数字须附产生命令"约束**（写 `mode600=0` 就得附 `find . -type f -perm 600`）。

### 5c. ★ 「引用反查」必须覆盖本批**每一个**被改文件；「收口」的判据是**不变量成立**

**（a）反查要覆盖本批改动的每一个文件，不是只查主目标**
- 实测：一批改了 **2 个文件**（A、B），却**只反查了 A** 的"当前"引用 ⇒ 同步了引用 A 的登记行，**漏掉引用 B 的那一行** ⇒ 那一行立刻 stale。
  （具体：改了「坑表 + 台账」，只补了引用坑表的那行，漏了引用台账的那行。）
- ⇒ 通则：**凡本批改动过的文件，逐个反查"有哪些『当前/现行』类登记引用了它"，一并同步。**
- 与前一条合起来才是完整流程：
  **① 先查**（要改的文件被谁引用）→ **② 定范围** → **③ 再反查**（本批**实际**改动的每个文件被谁引用）。

**（b）「收口」的判据是「不变量成立」，不是「步骤做完」**
- 实测：某批自报"治理收口、当前类零 stale"，**而同一批自己的连带效应**（改了台账 ⇒ 台账行数变 ⇒ 引用它的登记行 stale）**立刻造出一个新的 stale**。
  ⇒ 通则：**在宣布"收口 / 零 stale / 全部同步"之前，必须让那个"不变量"本身被核验过**
  （例：整表逐条与现行值比对），**不能以"我这批的步骤都执行了"当判据**。
- 推论：**"当前"类登记表不要"逐条补"，要"整表核"** —— 逐条补永远追不上，因为**每次改动都会新造 stale**。

### 5d. ★ 勘误要沿「结论引用链」传播；引用要锚内容、不锚行号

**（a）勘误 / 口径变更必须沿「结论引用链」传播**
- 改了源文档**不算完**：必须**反查所有复述它的地方**（摘要 / 总览 / 汇报 / 结论章），逐一处理
  （体例：**原句不改 + 紧随一行勘误**，保住历史）。
- 实测：某错误在源文档**已勘误**，但**"读者入口"那一份仍留着旧数字** —— 同一结论在该总览里有 **≥4 处**复述，
  而当事人**只报了 2 处**。⇒ **「我看到的」不能作为传播范围**，传播范围必须由**反查**确定。
- 后果：**旧数字会留在最容易被读到的地方**（越是摘要/总览，越先被读）。

**（b）引用要锚「内容 / 语义特征」，不锚「行号 / 位置」**
- 行号是**会漂的位置**：文件一增删，你引用的"第 N 行"就不再是你以为的那一行。
- 实测：核某登记行时按"**第 109 行**"去读，而该文件已从 **155 行长到 169 行** ⇒ **读错了行**，核对结论当场失效。
- ⇒ 通则：**跨文件引用 / 核对一律按内容定位**（`grep 语义特征` 再读）；行号只能作为**当次输出**里的定位提示，
  **不得跨时点复用**。

### 5e. ★ 「现行值」必须单一权威 + 指针；同一批内不得既改 X 又写 X 的现行值

- **无不动点**：**你改动了 X，又在同一批里写死"X 的现行值"** ⇒ **写完就旧** —— 补一次落后一次，**无穷回退**。
  （与「载体自报自身哈希无不动点」同族，只是从**自指**变成**同批自涉**：改的是它、写的也是它。）
- **解法（唯一能终结回退的）**：**"现行值"只能有一个权威归属地**，其余位置一律二选一：
  - **指针式**：「现行见 <权威载体> §X」；或
  - **带时点的检查点**：「（<批次/日期> 后；**非现行**）= `…`」—— 带时点 ⇒ **事件属性** ⇒ 永远为真 ⇒ **可以保留**。
  ⇒ **一律不得留「无时点的硬编码现行值」。**
- ★ **配套：不变量断言的覆盖面 = 「本批改动对象的全部『当前』类引用点」**。
  实测：某批的跨文件断言**只覆盖了行数**、**没覆盖"散文里的 md5 值"** ⇒ 散文里 4 处"现行 md5"当场过期，而断言**全绿**。
  ⇒ **断言漏掉哪一类引用点，那一类就会静默过期。**
- ★ 正面意义：**与其每次"适配"一个必然过期的值，不如把它换成不会过期的东西** ——
  这是对「被放宽致死」（误报 → 放宽 → 守卫失效）的**正向对照**：**治本 = 换锚；不治本 = 反复适配。**
- ★★ **「双记」只在"引用的是当前值"时才需要 —— 别见到旧值就默认要双记。**
  实测：某表以**实例证据**的方式引用了另一份文档的 md5（形如"P-0xx 实例：某文档 md5 = …"）。
  ⇒ **先判类别**：**事件引用**（描述"某次实例**当时**的取值"）⇒ **不动、也不双记**
  —— 因为**"双记"的目的是"补历史"，而事件引用本身就已经是那条历史**（再补一次是重复）；
  **现行引用**（说"**当前**是 X"）⇒ 才需要双记「历史值 → 现行值」或改为指针。
  ⇒ **把"判定类别"当成一个必须显式执行的步骤**，不要跳过它直接去改文档。
- ⇒ 配套的一条：**"归谁改"看"谁现在持有该载体的写入权"，不看"这文件原来是谁建的"。**
  实测：一份文件不在某人的派工清单内，但**它位于该人负责的线目录下、且改动只是"原句不改 + 紧随一行"**
  ⇒ **由他改是对的**（按"**单一写入者**"划权，而不是按"历史归属"划权）。
- ★★ **更优解：与其把"判定"做对，不如让"判定"不再需要 —— 改造对象，而不是改进判据。**
  实测：我裁定「先判该引用是**事件**还是**现行**，前者不动、后者双记」；执行方给出的**第三条路更优**：
  把旧值改写成「**YYYY-MM-DD 执行时值 · 非现行**」（**带时点的检查点**）
  ＋ 附「**现行值一律现算**（对文件现跑 `md5sum`）」的**读取规则** ＋ 声明「**本表不硬编码**」
  ⇒ **该引用自此自带类别标签，也自带"现行值怎么取"的答案** ⇒ **我要求的那一步判定从此不存在**。
  ⇒ 通则：**当"判定某对象的类别"本身很费劲时，优先改造对象让它自带标签** ——
  **目标不是判得更准，而是让这个问题不再需要判。**
  ⇒ 这与"**与其反复适配一个必然过期的值，不如换成不会过期的东西**"是**同一条思路的两个面**：
  ① 对值 ⇒ 换成**不会过期**的形式；② 对判定 ⇒ 换成**不需要判定**的形式。**两者都属"改造"，不属"诊断"。**

### 5f. ★ 「要改的点的清单」必须由机器枚举；不变量里的「0」必须先定义「什么算命中」

**（a）清单要机器枚举，人列的只是抽样**
- 同一类错在同一个项目里**连续出现三次** —— **人肉列"要改的点"，每一次都不全**：
  ① 划"只动 N 个文件"的边界 ⇒ **漏**（实际必须多动一个）；
  ② 列"引用了旧 md5 的位置" ⇒ 给 **1** 处、**实 5 处**；
  ③ 列"散文里的裸「现行」md5" ⇒ 给 **2** 处、**实 6 处**。
- ⇒ 通则：**凡"要改 / 要核的点"的清单，必须由脚本或断言枚举产生**；人只负责**确认**与**定义判据**。
- ★ **正面样板**：把"**散文里的现行 md5 残留 = 0**"直接写成一个**断言** ⇒ **枚举由机器完成** ⇒
  一次抓全（比人的清单**多出 3 倍**），而且下批自动复核。

**（b）不变量里的「0」必须先定义「什么算命中」**
- 一个不变量宣称"**残留 = 0**"，若**没写清"什么算命中"**，那个 0 **不可信** —— 它可能只是**判据太窄**。
  实测：某断言只覆盖"文中硬编码的 md5"（范围偏窄）；**按更宽的"『现行』后紧跟 md5/行数"重扫则得较多数目**
  （其中多数是**无关语义**与**合法的历史语境**，本不该算命中）。
- ⇒ 通则：**不变量必须同时给出「判据定义」与「计数」**；**判据太窄 ⇒ 永远 0 ⇒ 变相「恒否判据」**（见 7c）。
- ★ **附带一个具体的精度陷阱：子串 / 前缀扫描必须处理「边界」**。
  实测：用 `113 行` 去扫，会**误命中 `2113 行`**（纯子串匹配）⇒ 计数被抬高，而**抬高的是"假命中"**。
  ⇒ 注意这是**同一问题的另一侧**：**判据太窄 ⇒ 假阴性（永远 0）；判据太宽/无边界的子串 ⇒ 假阳性（虚高）**。
  ⇒ 做法：**加边界条件**（前后非数字）、或**用带定界符的模式**（如 `(^|[^0-9])113 行`）；
  并在报告里**写明命中口径与边界规则** —— 让"0"和"非 0"都可解释。
- ★★ **并列数列必须逐个给「行 / 层标签」**。
  实测：我在一份事实表里写「`ratio = 4.72 / 4.12 / 3.47`；过 FDR = `2,807 / 154 / 106`」——
  **没给行标签**，而它们其实是**同一张表的三行（三个不同的网格）**，**不是「三档」、也不是「三轴」**。
  ⇒ **读者只能靠排列顺序去猜，而排列顺序会诱导出错的猜法**（这里极易被读成"三档"）。
  ⇒ 通则：**凡并列 ≥2 个数，每个数都要能回答"它是哪一行 / 哪一层 / 哪个口径"**；
  **宁可把标签重复三遍，也不要让读者去猜。**
- ★★ 同族的一种更隐蔽的错：**跨层并列**。
  实测：一句话里同时放了「合取层 199 对（阴性）」与「网格层 28,329 分母」——
  **两层不是同一个分母**，读者会把它们当成"同一件事的两种说法"。
  ⇒ 做法：**先写层名，再写数**；**两层结论方向可以不同，但必须并列陈述，不得互相覆盖**
  （如"合取层有 4 对过 FDR（指向 X）；但中介效应层 199 对 CI 全含 0"）。
- ★★ **用关键词检查「禁用词 / 违禁项」必然产生假阳性 —— 因为禁用清单自己就包含这些词。**
  实测：一份新文档里 `关联` 命中 3 次、`提示性信号` 1 次、`有趋势` 1 次，**看起来像违规**；
  逐处看上下文 ⇒ **全部是「规则陈述」与「禁用清单」自身的出现**，**无一处是违规使用**。
  ⇒ 通则：**查"禁用词是否被违规使用"不能只数命中** ——
  ① **逐处看上下文**；② **把「清单 / 规则陈述的自指出现」显式排除**；
  ③ **报数时同时报"其中几处是规则自指"**（否则读者会以为出了问题）。
  ⇒ 更一般地说：**判据若建立在"禁词表"之上，就必须自带「豁免项」**（豁免 = 禁词表本身）；
  否则这个判据**从设计上就注定报假警**。

## 二、门禁与验证

### 6. ★ 门禁类工具**必须先做「故意的失败测试」**
**未做过失败测试的门禁，不得作为放行判据。**
- 做法：用**已知会失败**的输入喂它，确认它**拦得住且退出码非 0**；再用干净输入确认它**不误报**（防过度收紧）。
- 防的是：立了「rc=0 才放行」的纪律，却从没验证过门禁拦不拦得住 —— 结果是**空门**，坏输入一路放行。

### 7. 门禁的「通过」必须意味着「**确实检了东西且都检过了**」
- **扫到 0 个文件 ⇒ 必须失败**（"没检" ≠ "检过了"）。
- 输出必须能**自查**：并列打印 `FILES_SCANNED / PARSE_FAIL_N / FILES_PARSED`。
  - 只打「成功解析数」是危险的 —— 它恰好等于「排除坏文件后的剩余数」，**空门就藏在这里**（数字看起来正常）。
- 退出码**统一用 1**，不引入多级码（消费方只判 `rc != 0`，多级码没有消费者、只增加误读面）。

### 7b. ★ 守卫必须锚「你在意的那个不变量」，不要锚「整个载体的哈希」

- **失败模式（命名：被放宽致死 / relaxed-into-vacuity）**：守卫**一开始确实会拦**，但它锚在一个**合法漂移的对象**上（最典型 = "**活文档**的整文件 md5"），于是**每次合法改动都误报**；
  为了让流程能走，人们开始"适配"它（改常量、加白名单、改成 `|| true`）—— **改到第 N 次，它就只等于"某人最后一次摸它的时刻"** ⇒ 退化成**空判据**。
- 与**形态 1「空门」**的区别就在"**曾经拦过**"这个字：空门是一开始就不拦，这条是**被自己的误报率喂死的**。
- **根因**：锚错了载体。"文件哈希"回答的是"**这个文件变没变**"；而你要问的是"**我依赖的那个不变量还在不在**"。活文档漂移是**合法**的，成员集合漂移才是**不合法**的。
- 正解：**换成语义锚** —— 从载体里**解析出你真正依赖的那个集合/字段**，断言它与预期**相等，并在失败消息里报出差集**。
  实测：某脚本用"源文档整文件 md5"当守卫，我方按纪律追加一次勘误，该脚本**下次重跑必然 ABORT**（一个沉睡陷阱）；
  改成"**解析出成员 accession 集合 == 脚本内硬编码的 19 条**"后 ⇒ **勘误/追加不再误报，而成员集合一变必然拦下**。
- ★ **换锚之后必须做「双向」测试**：
  ① **该拦的拦得住** —— 改掉集合里一个元素 ⇒ 必须 `ABORT`（贴真实输出、含差集）；
  ② **不该拦的不误报** —— 往载体里加一行无关文字 ⇒ 必须**仍通过**。
  **②这一半才是新判据的全部价值**；少了它，等于没换。
- 附：**回滚不是选项** —— 明知会误报还留着，等于把"下次必炸"当特性。要修就修锚，不要修数据。

### 7c. ★ 判据必须「两端可达」—— 门禁要能返回 FAIL，筛查要能返回 HIT

- 与 7b 互为镜像的另一种失效：**恒否判据** —— 一段判定**永远返回"没有 / 不通过"**，**结构上不可能报出阳性**。
  实测：某复核判据写成 `awk 'NR>1 && $12+0>0.8'`，而被判文件**只有 10 列** ⇒ `$12` 恒为空串 ⇒ 空串转 0 ⇒ `0 > 0.8` **恒假**
  ⇒ **该命令在任何输入下都返回 0 行**。
  ⇒ 最危险的地方：**真实答案恰好也是 0** ⇒ **巧合正确**，于是没有人会去查判据本身。
  **一个错误的判据给出了正确的答案，是最难被发现的一类错。**
- 与「空判据」的分工（互为镜像）：
  - **空判据**（形态 6）= 永远"**通过**" ⇒ 给**假安心**；
  - **恒否判据** = 永远"**无发现**" ⇒ 给**假阴性** —— 对**筛查型**任务更坏，因为它把"**我没找到**"伪装成"**没有**"。
- ★ **通则：判据必须两端可达** —— 门禁类必须**能返回 FAIL**；筛查类必须**能返回 HIT**。
  否则它测的不是对象，而是**判据自己的盲**。
- ★ 推论（列号 / 字段名）：**凡判据引用列号或字段名，必须先把"它存在"验掉**。
  多数工具对"读不存在的字段"是**静默**的（awk 空串 → 0、按列读少列 → NA/`NULL`），**不报错**。
  做法：先 `head -1` 打出表头并**数出列数**（本例 `NF=10`，一眼就能否掉 `$12`），**能用列名就不用列号**。
- 附：**坏判据宁可"报假警"，不可"恒沉默"** —— 前者会被修，后者会被信。
- ★ 同族的第二个实例（更常见）：**"读错字段"的主要形式不是列号错，而是"分隔方式错"**。
  实测：对一个含**引号内逗号**的 CSV 用裸 `awk -F','` 切分 ⇒ **整行错列** ⇒ 计数得到 **`0/57`**（错的，而且是个**假阴性**）；
  改用真正的 CSV 解析器（R `fread`，或 Python `csv`）才是 **`8/57`**。
  ⇒ 通则：**CSV 一律用真 CSV 解析器，禁止裸按分隔符切**；
  ⇒ 且注意 **"字段存在" ≠ "字段对齐"** —— 列确实存在、但整行错位时，**照样是读错**。凡判据引用字段，**存在性与对齐性都要验**。

### 7d. ★ 同语义多实现，必须指定「规范」并把其余登记为 port

- 场景：同一道保证要在**两种技术栈**里各实现一遍（实例：bash 门禁片段**无法**贴进 `.R` 文件，于是写了"R 侧等价"）。
- 风险：**两套实现都声称同一件事，却没有任何机制保证它们一致** ⇒ 必然漂移，且漂移时**没人会发现**（两份都"看起来是对的"）。
- 规则三条：
  1. **指定唯一 canonical（规范）**，其余**全部**是 **port（派生）**；
  2. **两侧头注互相指向**：port 侧写「本文件是 `<canonical 路径>` 的 port，**规范以它为准**；canonical 变更时本文件必须同步复核」；
  3. **维护一张 port 清单**（载体 / 文件 / port 时对应的 canonical 版本或 md5）。
- ★ **"只查启动集 / 活跃集"优于"扫全目录"** —— 全目录扫描会被**死代码、废弃脚本**钉死 ⇒ 大量**假警报** ⇒ 守卫随后被"**放宽致死**"（见 7b）。
  **这条线把 7b 与 7d 连起来了：假警报 → 放宽 → 守卫失效。**

- **附（工具层，同一族：别把"显示假象"当成"数据问题"）**：核验中文 diff 时**不要用 `cut -c` 截断** —— 在非 UTF-8 locale 下它**按字节切**，会把中文切成半个字符，**显示成乱码**，极易被误判为"文件编码坏了"。
  正确做法：要判编码就查真值（`file -bi`；或 `python3 -c "open(f,encoding='utf-8').read()"`），**不要拿终端渲染当证据**。

### 7e. ★ 「自指哈希」没有不动点；「空操作修复」不算修复

**（a）载体自报自身哈希 ⇒ 无不动点**
- 在一个文件里写「**本文件自身的 md5 = X**」是**自相矛盾**的：写进去之后它的 md5 就变了 ⇒ **永远不存在一个能自洽的值**。
  实测两次：① 变更记录行内嵌「本普查自身的新 md5」⇒ 写入即失效；② 脚本内置 `SELF_MD5 <- md5sum(自己)` ⇒ **脚本一改、产物 md 必变**。
- ⇒ 通则：**自身哈希只能记在**别的载体**上**（登记处 / 台账 / 侧车 `.meta`）。
- ⇒ 更深一层：**凡"载体自报自身同一性"都无不动点** —— 与「心跳的载体必须与主进程共生命周期」同族（**自指必然产生矛盾**）。

**（b）`replace(X, X)` = 「空操作修复」**
- 形式像修复，实则**什么都没改**。⇒ 它是「**假门**」在**修复动作**上的镜像：假门是"判据不阻止"，空操作修复是"**修复不改变任何东西**"。
- ⇒ 通则：**任何"修复"必须能证明它改变了某个可观测量**（md5 / `diff` 行数 / 测试输出）；**证明不出来 ⇒ 按"未修"处理**。
- ⇒ 与「会失败的断言才是资产」互补：**断言要能失败，修复要能改变** —— 两者的共同要求是"**必须存在一个可观测的差异**"。

### 7f. ★★ 判据的**维度**可能选错 —— 单维指标替代不了多维的「可辨性」（2026-09-24 实测）

**事故**：契约某节写着「有序层次 C1→C2→C6→C5→C4，**相邻明度差 ≥25%**」。执行方实测算出"4 段里只 1 段达标" ⇒ 报告"该判据不成立"，并提两个修法：(a) 放宽为 relLum 比 ≥1.25×；(b) 改序为明度单调。

**两个修法都不对**，因为它们都在**保留错误维度**的前提下打补丁：
- (a) 放宽后 C2→C6 = 0.41× **仍不达标** ⇒ 判据还是废的，只是把"4 段全废"改成"1 段不废"；
- (b) 改明度单调序后，**C1→C6 的 ΔL\* 只有 2.71** ⇒ 得 1/4 段达标，**比原来更差**。

**真因：维度选错了。** 独立算 CIELAB 后看到：

| 段 | ΔL\* | ΔE(CIE76) |
|---|---|---|
| **C2→C6**（橙 vs 蓝） | **20.19**（明度几乎一样） | **86.57**（一眼可辨） |
| C5→C4 | 7.94 | 30.50 |

**「有序层次」要保证的是「相邻两层能被一眼分开」，这是三维色差问题，不是单维明度问题。** 拿明度判 C2→C6「不合格」，**是判据错了，不是色错了**。

**⇒ 正解是换维度**：判据改为 **相邻 ΔE(CIELAB) ≥ 20**。原序实测 24.12 / 86.57 / 40.60 / 30.50 ⇒ **全部合格，序一个字都不用改。**

**同族**：这是判据家族**第四种**失效形态 ——
1. `awk $12`：**列不存在**（判据指向了不存在的字段）
2. `gregexpr` 恒 ≥1：**实现错**（永远返回真）
3. `MAX_COMP_AREA` 跳过：**取值范围错**（把要检的对象排除了）
4. **本条：维度错**（实现对、数据真，但**检的不是那个该检的性质**）

⇒ 前三种在"喂一个显然该失败的反例"时会暴露；**第四种不会** —— 因为它在自己的维度上**算得完全正确**。

**判据**
1. 当一条判据"大面积不达标"时，**先质疑判据的三个要素**：① 域（检的是不是该检的对象）② 实现（能不能返回假）③ **维度（这个量能不能代表你要的性质）**。
2. **凡"可辨性 / 可读性 / 相似度"这类要求，禁止用单维指标判** —— 用欧氏色差、面积、CI 宽度等**多维量**。单维只能做**粗筛**，不能做**判据**。
3. 阈值里的百分比**必须写明绝对还是相对**（本事故"≥25%"按绝对读是 1/4 段、按相对读是 3/4 段 —— **同一句话两种读法结论相反，这条判据本身就是废的**）。

### 8. 判「作业是否在推进」看**累计消化量**，不看日志、不看 load
- 用子进程 `read_bytes` / 产物增量判断。
- 反例：日志 21 分钟无新行 + load 很高 ⇒ 曾误判「空转」，实测 `read_bytes` ≈130 GB、盘速 115 MB/s ⇒ **正常推进**。
- 同时注意：**log mtime 可能因块缓冲冻结** ⇒ 禁用 log 判存活。

### 9. 「等 pid 退出」**无法区分「跑完」与「被 kill」**
- 守望脚本必须额外校验**产物完整性**（行数 / 断言 / `.done` 内容），否则会拿**未完成的产物**收尾并写**假完成标记**。
- **kill 顺序**：**先杀守望，再杀作业**。反了就会触发上述假完成。

### 10. 并发写入同一文件 ⇒ 单一写入者
多人同时 append 一个文件会造成**编号撞号 + 版本错位**（实测：两人分别看到 7 条与 20 条两个版本；一人提议的新编号已被另一人占用）。
- 处置：**指定唯一写入者**，编号由写入者分配，他人只提交内容。
- 并发下「**先取 md5 守卫 + 先 `cp -p` 备份**」是必要动作。

### 11. ★★ 「脚本已改」≠「产物已改」—— 判据是 **mtime 序与内容命中**，不是任何一方自述（2026-09-24 实测）

**事故**：执行方回报「A 组 7 张已收口（字体、版式、命名、图注四项）」。我独立扫盘实测：

| 对象 | mtime |
|---|---|
| `fig6_build.py` | 13:51 |
| `fig8910_scatter.py` | 13:52 |
| `fig11_build.py` | 13:53 |
| **产物 svg：fig6** | **13:47** |
| **产物 svg：fig8 / fig9 / fig10** | **13:07** |
| **产物 svg：fig11** | **12:30** |

⇒ **脚本全部晚于产物** ⇒ **改完根本没重跑**。再 grep 产物内部 hex：仍是上一版配色（`#e69f00` / `#0072b2` / `#d55e00`）。
⇒ 若不复核，「已收口」会被当作事实写进交付说明，而**盘上是五张过期图**。

**根因**：`编辑脚本`（有明确反馈：文件保存成功）与 `重跑产物`（无反馈，除非专门去看）之间，**存在一个静默断点**。人对「我改了脚本」的记忆，会**自动延伸**成「所以产物是新的」。这不是撒谎，是**认知上的就近替换**。

**判据（从弱到强，逐级都要）**
1. **`产物 mtime > 脚本 mtime`** —— 「重跑过」的**必要**条件（不充分）。
2. **产物内容里确实出现本次改动** —— 改色 ⇒ 在产物里 grep 新 hex；改标签 ⇒ 在产物文本层 grep 新串。**mtime 只证明「动过」，内容才证明「改对了」。**
3. **产物 md5 必须与上版不同** —— 若改了内容而 md5 不变 ⇒ 根本没写盘。
4. **收尾措辞**：**禁止**用「已收口 / 已完成」这类**无载荷措辞**结束一个多文件批次；必须逐文件给 `mtime + md5 + 关键内容命中`。

**同族**：与「报『已落地』前必须回读文件」同源，但**更隐蔽** —— 因为执行方**确实做了事**（改了脚本），只是没走完最后一步。**「做了什么」与「产出变了什么」之间的落差，是这套系统里最容易被漏掉的一环。**

**反向自保（lead 侧）**：收到「已完成」时，**先对产物做一次独立枚举**（mtime / md5 / 内容 grep），再决定是否往下走。**这一步几秒钟，省的是整批返工。**

## 三、统计与数据口径

### 11. ★ 分母 ≠ 实际检验数 ⇒ FDR 失真
登记的分母必须与**实际跑出来的检验数**一致。
- 计划暴露数 ≠ 实际可跑暴露数时，**分母用实际的**，计划值只作「注册计划」登记。
- 同理：若某类 id 因**面板缺文件**跑不出结果，那分母里含它就是虚的 ⇒ 必须在文档里点명。

### 12. 「阴性 / 不适用 / 方向未判定」三态**严禁混写**
- **阴性** = 前提成立、检验为负；
- **不适用** = 前提不成立、比例无定义；
- **方向未判定** = 方向检验不可靠。
- 典型陷阱：`PP.H4 < 0.2` 既可能是「都有关联但不共享」（真阴性），也可能是「结局侧根本没信号」（不适用）。**必须先看 `PP.H2` 分层再下结论。**
- 报告里要写清是「**在可检验的 N 对里**结论如此」，还是「**大部分对根本不可检验**」—— 证据强度差很远。

### 13. 单工具 / 单 SNP 撑起的信号，**不得单独下结论**
- 强制做 **drop-top-weight**；单工具时**显式写 `N/A(单工具)`**，**不得静默跳过**。
- 也要写清「**N 对共享同一工具 ⇒ 非独立检验，有效自由度远小于 N**」，防止被读成「N 个独立发现」。

### 14. 多口径并存时，**并列 + 明标主口径**
不同 FDR 分母会**翻转结论**（实测：某基因在按基因的分母下 0 个通过、在主方法池下 2 个通过）。
- 输出**加 `denominator_set` 列**，并**显式标出「主口径 = X」**，防下游拿副口径当主结论。
- 汇总层与明细层不一致时，**以明细为准**，并在汇总层回改或注明。

### 15. ★ 起跑前**先算读量**，再选读法
- 只需少量键的抽取，一律「**1 遍 + 流式过滤**」；禁止整表载入 × N 次。
- 实测教训：外层基因/内层结局的嵌套循环 ⇒ 面板被读 15 遍 = **7.56 TB**；21×1400 的整表解压估算 ≈ **9.9 TB / 188 h**；改成「结局外循环」⇒ **1 遍 / 1.5 h**。
- 把**读量估算写进日志首 3 行**，让复核者能判 ETA。

### 16. 瓶颈是单块机械盘时，「核数 ≈ 倍数」是错的直觉
- 实测：`B(8) ≈ 100 MB/s > B(17) ≈ 64 MB/s`（流越多、寻道越重、聚合反降）；16 路只比 4 路快 16%。
- **加并发只改变分摊方式，不改变总供给**；要提速只能**减少总读量**。

---

### 16b. ★ 「构造保证」不是「经验发现」；且过滤条件必须比**全部**相关键

**（a）构造保证 ≠ 经验发现**
- 场景：某属性其实由**上游构造步骤强制**（真实例：挑暴露工具时**已写死** `|SNP位置 − 基因位置| ≤ 1 Mb`）。
  下游再做一次"独立复核"、得到 **100% 符合** ⇒ 这**只是一致性检查**，**不是"发现了 cis 富集"**。
- ⇒ **必须把这句话留在文档里**：否则后来的读者（包括三个月后的自己）会把"**上游的假设**"读成"**下游的证据**"。
  **把"构造保证"当成"经验发现"，是一种很常见的虚假发现。**
- 做法：报告里凡出现"100% / 全部符合"，先自问一句：**这是被构造保证的吗？**
  是 ⇒ 写成"**与上游约束一致（独立复核）**"，**不写成"我们发现"**。
- 附：这种"独立复核"仍有价值 —— 它的价值是**不信任构造代码、用原始数据重推**（可发现构造代码本身的 bug），但**价值的性质是"校验"而非"发现"**。

**（b）"位置/区间"类过滤必须同时比**染色体**，不能只比位置差**
- 实测缺陷：一段 cis 窗过滤写成 `abs(SNPPos - tss) <= cis_kb*1000` —— **只比位置差、没有 `SNPChr == GeneChr`**
  ⇒ **跨染色体的"等位位置"会误入**。（该次实测 **0 个中招**，但那是**运气**，不是**保证**。）
- ⇒ 通则：**凡"位置/区间"过滤，必须同时校验染色体**；且**"没出事" ≠ "没缺陷"** —— 报告里两句话都要有。
- ⇒ 配套：修这类缺陷**必须做双向失败测试** —— 造一条"**同位置不同染色体**"的反例，要求**修前必须被放进、修后必须被拦**。**只测一面等于没测。**
- ⇒ 反过来也成立：**一个判据要在两条线上给出相反结论，才算证明它"两端可达"**（实测：同一份 cis/trans 审计脚本，在 A 线得 100% cis、在 B 线得 0% cis ⇒ 它测的是对象，不是自己的盲）。

## 四、跨域 id 与断言

### 17. 同一个 id 域可能有**两种合法解释**（联合池成员 vs 子网格成员）
- **不能仅凭「id 落在主域之外」就判为「越域污染」**。
- 判定前**必须先读登记表与口径文档里对该域的定义**。
- 反例（真实事故）：把「1400 代谢物 + 91 蛋白 = 1491 联合池」预注册设计误判为污染并剔除 ⇒ 删掉了**合法数据**，还要回滚。
- **教训的变体**：不只"引用不存在的东西"会出错，**"引用了存在的东西但没读内容"同样会出错**。

### 18. 用「**实读清单**」而不是「硬编码区间」做域断言
- `list.files(dir)` 提取 id 清单 ⇒ 能同时抓住「**面板缺文件**」；
- 硬编码区间 `A..B` 会在面板缺文件时**放过缺失的 id**。
- 断言里**打印 union 的实际大小**，这个数本身就是「面板完不完整」的证据。

## 五、环境与迁移

### 19. 默认值里出现**本机盘符路径**（`C:/` `D:/` `E:/`）＝ 迁移残留信号
- 症状：迁移到服务器后**静默 BLOCKED**（路径不存在，但不报错）。
- 检查项：同一项目内**多处 `Sys.getenv` / `os.environ.get` 的默认值是否一致**（实测：一处已改对、另一处没改 ⇒ 故障）。
- 迁移时**全局 grep 盘符**。

### 20. 缓解方案要验证「**不会破坏别的依赖**」
- 反例：建议用 `--vanilla` 跳过配置，**但它含 `--no-environ` ⇒ 会丢掉认证 token** ⇒ 在线取数全废。
- 反例：`--no-init-file` **既不解决根因**（问题源在包的 `.onAttach`），**又与「在配置文件里装补丁」的方案互斥**。
- 定案前先做**互斥性检查**：两个缓解措施是否互相拆台？

---

### 20b. ★ 环境变量会在「进程边界」静默丢失 —— 控制开关与凭据不要靠它

- **实测同族三次**：
  ① **`ssh` 默认不转发本地环境变量**（需 `SendEnv`/`AcceptEnv` 且服务端允许）⇒ 远端读到"未设" ⇒
     **一个"干跑"开关失效、干跑变成了真跑**。★ 这次没出事**是运气**（脚本内断言恰好全为真），**不是设计保证**。
  ② **`R --vanilla`**（含 `--no-environ`）⇒ **丢掉 `OPENGWAS_JWT`**。
  ③ **`sudo` 默认重置环境**（`env_reset`）⇒ 上游 env 传不进去。
- ⇒ 通则：**凡"靠环境变量传递的控制开关 / 凭据"，必须验证它真的到位** ——
  **脚本开头断言非空 / 把它打印出来**；**跨进程边界的关键开关，改用命令行参数**
  （**命令行参数不会被 `ssh` / `--vanilla` / `sudo` 吃掉**）。
- ⇒ 定性：这属于「**安全机制静默失效**」家族 —— "干跑"是一种保护，**保护失效 = 加固失效**。
- ⇒ 配套纪律：**"干跑"必须留下可观测凭证**（打印 `DRY-RUN`，且**不产生任何写操作的可观测副作用**），
  否则**无法区分"干跑了"与"以为干跑了"**。

### 20c. ★★ 中间文件**禁止写入用户主目录**（实测：11 天累积 900+ 件）

**实测**：某次连跑 11 天后，用户主目录第一层堆到 **1,400+ 文件 / 60+ 目录**，其中
**`_` 开头的临时件 900+ 个**，时间跨 09-13 → 09-24。多个 agent 把脚本与输出直写主目录，
把它当成了公共草稿纸。

⚠ **其中十余件 `.md` 是「留痕文档」**（patch 应用记录、搬运校验记录、对表、代码说明）——**不可批量删**。

**规则**
1. **中间文件一律写自身工作区或项目目录**（范本：`任务/<年月>/<任务名>/_tmp/<成员>/`），**禁止直写用户主目录**。
2. **处置存量时：扫描 = 只读**（只出盘点报告）；**移动/删除必须在用户明确指定范围后才执行**，优先走回收站；**留痕文档归档而非删除**。
3. **同一目录多 agent 并发写是真实存在的**（本会话出现 3 次"疑似第三方"误报，**全部是自己**）⇒ **上报"疑似第三方"前，先在自己最近 1–2 条回报里 grep 那个文件名/md5**。

### 20d. ★★ 复合命令里的**每个工具调用都必须单独检查返回码**

**事故（实测）**：执行方报「某文件在两步之间被外部删除」。真因是
**复合命令里 `cp` 与 `python` 写在一起，PATH 未就绪 ⇒ `cp: command not found` ⇒ 文件根本没生成**。

**规则**
1. **把多步命令拆开**，或**每步单独判 rc**（`a && b || { echo STEP_A_FAIL; exit 1; }`）。
2. **报"文件消失/被删"前，先证明它「曾经真的存在过」**（生成成功的证据：rc、回读、md5）。
3. 与「§9 等 pid 退出无法区分"跑完"与"被 kill"」同族：**"结果不符预期"要先排除"上一步其实没成功"**。

## 六、汇报纪律

- **报「已落地」前必须回读文件确认**（实测出现过「报告与实况不符」两次）。
- **不要只信自己刚写的校验逻辑**；最终以独立手段（如逐字 md5 比对）为准。
- **核验产物必须看上下文**：`grep -c` 的命中可能是声明句/图例/留痕，不是实际结果（实测因此误报 4 次）。
- **ETA 估算**：短窗增量要**除以真实增量**再外推（实测：把「121 s 内多 2 个文件」当成「每文件 121 s」，报 39–44 h，实际 18–21 h）。
- 向用户交付时，**主动说明自己判断错误的地方**，不要只报顺利的部分。

### 交接与指令（长文是最容易被忽视的故障源）

- **★ 指令要短、要编号、要可勾选。**
  实测：给同一队友连发三条长消息后，他把**已经被裁定过的三项**又重新列为"待你裁决" —— 说明**关键指令被自己的长文淹没了**。
  ⇒ 做法：**一次只交代一件事**，或多件事时给**一张带编号的表**；**绝不要把交接物埋在长文的第四节**。
- **★ 交接物必须单独成条，并在转发时标注「这是交接物，请确认收到」。**
  实测：A 的正文经"我"中转发给 B，B 判定"未收到独立正文"，于是从**权威产物**（脚本头注）忠实转录重建 —— 结果对，但过程暴露**中转环节会丢东西**。
  ⇒ 铁律：**中转发出的关键物，必须请接收方回执一句「已收到」**；无回执即视为未送达。
- **交接物缺失时，去找权威源重建，不要空等、不要猜写。**（上例里 B 的做法，值得当作规范。）
- **任务"完成"的判定要以交付清单为准，不以执行方的自我标注为准。**
  实测：队友两次把任务标 `completed`，但清单里 A–G 有两项（入口盘点、断言落位）从未开始 —— 他的收口报告本身质量很好、md5 齐全，**只是漏了两项**。
  ⇒ 做法：**派单时写明"完成 = 下列 N 项全交付"**，收口时**逐项勾选**，而不是看"报告已发"。

### ★ 汇报通道与「巡检受阻」的定性（2026-09-24 实测）

**① `SendMessage` / agent-mail 在本机不可用 —— 团队通道是本地 JSON 收件箱。**

- `mcp__agent-mail__GetMe` 返回 `{"status":"not_bound"}`（**Agent 邮箱未开通**）⇒ **不要**再尝试邮件类工具。
- 真实通道：`~/.workbuddy/teams/<team>/inboxes/<成员>.json`，内容是**一个 JSON 数组**（`<team>` 取团队名，`<成员>` 取成员的 Agent ID）。
- 元素字段：`from / text / summary / timestamp / color / id / read`。
  - `timestamp` 用 **UTC** ISO 8601 + 毫秒 + `Z`（如 `2026-09-23T18:12:46.702Z`），**不要写本地时间不加时差**。
  - `color` 实测合法值：`blue / magenta / green / cyan / yellow / red`（`system` 通知不带 color）。
    告警用 `yellow`；确诊硬件命中用 `red`。
- **写入纪律与改文档同级**：`shutil.copy2` 备份为 `.bak_autoreport_<原因>_<日期>` → append → `json.load` 回读；
  记录「改前 md5 == 备份 md5 ≠ 改后 md5」+「条数 N → N+1」。任何一步跳过都不算送达。

**② 「连不上目标机」必须先归因，不得直接定性为故障或正常。**

- 必查三件套：本机 IPv4/网关、`route print -4` 有无目标网段路由、公网是否可达。
- 实例：本机连在 `192.168.43.0/24`（**手机热点默认网段**），而目标机在另一个内网网段（如 `192.168.3.0/24`）——
  不同网段 ⇒ 到目标机 **必然 100% 丢包**；而公网与热点网关均 0% 丢失 ⇒ **本机网络本身是通的**。
- **能得出的结论只有「本机连不上」**；由此**不得**推断「服务器故障」，也**不得**推断「服务器正常」。
  目标机的磁盘/进程状态一律标 **「未知」**。
- ⇒ **巡检类任务出现"跑不了"时，不得为了台账连续而补写一行"正常"** ——
  台账的每行语义是「**已检且正常**」；写 N/A 或空缺填充等于把「没看」记成「看过」。
  正确做法：**如实报"受阻 + 盲区时长"**，并明确请求裁决（补跑 / 口径如何算）。
- **★ 区分「巡检间隔」与「盲区时长」**（2026-09-24 实测踩坑，已发更正）：
  盲区 = **观测手段真正停摆的时长**，**不是**「距上次成功巡检过了多久」。
  实测错例：把「两次巡检相隔 6 h」报成「盲区 6 h」——**实际缺口只有 7 分钟**（且重试即自愈）。
  - 判定盲区要看**连续观测者（守护进程）的日志有无断档**（如 `chunk#N end` 与 `chunk#N+1 start` 是否同秒），
    而不是看两次 spot check 的间隔。
  - 定性前先看 `uptime`：`up N days` ⇒ 期间未重启，不可达与重启无关。
- **不要一见 `Connection timed out` 就发受阻告警**：**先重试**（间隔 ≥2 min、≥2 次）再定性 —— 自愈很常见。
- 报「无复发」这类阴性结论前，先问：**观测窗口完整吗？** 有盲区就不能算"未发生"。
- **更正要比原播报更醒目**：错误事实一旦播报，必须**主动广播更正并追溯全部引用点**（消息、记忆、注释），
  不要只在后续对话里悄悄改口。更正里要写清「错在哪 → 实情是什么 → 哪个推论作废」。

## 七、★ 通则：**不要判定一个你没打开看过的东西**

这是本项目一晚内**连续犯三次**的同一个毛病，单独立一条。

### 三种形态（都是同一个根因）

| 形态 | 实例 |
|---|---|
| **① 引用了不存在的东西** | 把 A 线的文档当成 B 线的；把"计划编号"当成已落成的章节 |
| **② 引用了存在的东西但没读内容** | 凭文件名/直觉判定某个 id 域是"纯代谢物域"，**没去读口径文档里对它的定义** ⇒ 把预注册的联合池误判为"污染"，裁决剔除了**合法数据** |
| **③ 只裁"要不要做"，没核实"对象存不存在"** | 对"某表里的某列""某文档的某行"下达处置指令，**而那个列/行其实不存在**（或被改名/被删） |

### 规则

1. **下达任何"改 A / 标注 B / 订正 C"的指令前，先把 A/B/C 打开看一遍。** 一行 `grep` 或 `sed -n` 的成本，远低于一次错误裁决 + 回滚。
2. **引用他人文件的内容时，读它、不要只看文件名。** 尤其当你要**据此下结论或做删除**时。
3. **对"某处应当如何"的判断，标为假设而不是结论**，并要求执行方**实测后回报**。
   - 好例：「我**预判** X 会失效 —— **请实测确认**」→ 执行方实测发现 X 没失效，但顺着判据找到真正失效的 Y。
   - 坏例：「X 会失效，请修」→ 执行方要么照改（白改），要么停下（浪费一轮）。
4. **回滚时，让被撤销的产物留痕**（另存 `.bak.<原因>_<时间戳>` + changelog），而不是悄悄覆盖 —— **回滚最难的不是改回去，是让后人看得出"这里曾经改错过"。**
5. **判断有反复是正常的**：担心被证伪 > 担心坐实。但**每次更正都要留痕并说明依据**，不得静默改口。

## 七之二、★★ 「未找到」≠「没有」—— 否定性结论必须附穷尽枚举（2026-09-23 实测，同一错犯两次）

**事故**：要核本机有没有 R 4.5.2。我扫了 `D:\R\R-4.1.0` 与 `C:\Program Files\R` 两层，没找到，**就在队内播报「本机没有 R 4.5.2」**，并据此把一条绘图方案从本机改到服务器（字体被迫降级为 Liberation Sans）。
**实情**：`D:\R\R-app\R-4.5.2\bin\Rscript.exe` **一直都在**，`library` **645 个包**，绘图所需包**一颗不缺**。我漏掉的是一个**容器目录** `R-app\` —— 它在 `D:\R\` 之下、`R-4.5.2` 又在它之下，而我用的 `*/library` 通配**只覆盖一层**，正好跳过。
**老板判定**：「**不是第一次这个问题了，严肃整改记入整个团队的记忆中**」。

**规则（四条）**
1. **只能说「（我）未找到」，不得说「没有」。** 前者是关于**我的搜索行为**的陈述，后者是关于**世界**的陈述 —— **前者推不出后者**。
2. **下任何否定性结论前，必须给出穷尽枚举的命令 + 它实际覆盖的搜索范围**；两者缺一，该结论**不得**进入任何文档、回报或方案。
3. **路径 / 环境类枚举必须覆盖"容器目录"**（`R-app` / `pack` / `versions` / `envs` / `opt` 这类中间层）；**深度不足以枚举全部候选时，明写「本次只扫了 X，未覆盖 Y」**。
4. **被播报过的错误事实必须广播更正，并追溯全部引用点**（文档、记忆、脚本注释）——★ 尤其是**它已经变成的那些"决策前提"**。错误的"事实"常常已经驱动了一串选择；**只改数字、不改决策，等于没改。**

**自查一句**：凡写出「没有 / 不存在 / 均不支持」时，必须紧接着能回答「**我找了哪些地方、用的什么命令、有没有覆盖容器目录**」。答不上来，就把它改回「未找到」。

**同族**：这与本项目那条「**面板里没有 ≠ 测了没找到**」是**同一条铁律的两种投影** —— 一条用于数据，一条用于环境。共同根因：**把「我的检索结果」当成了「世界的状态」。**

**顺带一条可搬用的教训**：**"我没找到"是关于我搜索行为的陈述；"没有"是关于世界的陈述。** 凡是把前者写成后者，都是同一类错误。

## 八、★ 「加固」自身的失效形态（实测五种，全部从表面上看不出来）

给系统加"门禁 / 断言 / 校验"时，**它们本身会失效，而且外观正常**。逐个打开看，不要靠"我记得加过"。

| # | 形态 | 典型实例 | 伪装 |
|---|---|---|---|
| **1** | **空门** —— 存在但不拦 | 静态检查器 `parse()` 失败只打日志、不计入失败、rc 仍 0 | 打印了检查输出 |
| **2** | **旁路** —— 有效但**不在生产路径** | 断言挂在 `05_xx.R`，而真正跑数据的是 `06_pipeline.R` | 代码正确、能 `stop()` |
| **3** | **假门** —— 在路径上、**还打成功**，就是不阻止 | `... 2>&1 \| tail -3` 吞掉退出码；无 `pipefail`；之后不判 `$?`、不 `exit` | 有输出、还打印 `_OK` |
| **4** | **假声称** —— 注释/记录**说**有门，实际没有 | 头注写"自带 `parse()` 自检"，全文无 `parse` | **让审查失效**（审查者会跳过"已自证"的东西） |
| **5** | **静默失效** —— 加固**动作本身**被吞掉 | 初始化期调用尚未 attach 的包函数（`assignInNamespace` 属 `utils`），被 `try(silent=TRUE)` 吞掉 | 脚本跑了、日志正常、文件也改了，**但没生效** |
| **6** | **空判据** —— **验证器本身**不读被验证对象 | 加固**未生效**的情况下，脚本照样打印 `XX_ON_OK`（判据是常量/空条件，不看计数、不看状态码、不看前后差值） | **"有验证"与"没验证"在日志上完全一样** |

**由此四条硬规则**：
- **门禁类工具必须先做「故意的失败测试」** —— 未做过失败测试的门禁，不得作为放行判据；
- **加固必须落在"生产路径"上**（先问：真正写结果的是哪个脚本？）；
- **验证必须靠"效果"，不能靠"脚本没报错"**（实例：数 connect 次数 0 vs 10）；
- **任何"宣布成功"的语句，必须绑定一个具体读数**（数字 / 状态码 / 计数），且该读数**必须能取到非预期值**（加固没生效时它必须会变）。
  ⇒ **"打印了 OK"不是证据；"读数在加固前后不同"才是证据。**
- 审计判据建议用**举证责任反转**：**"只有'文件改了/无报错'" ⇒ 一律视为「未加固」**。

**空判据的自检式（可自己跑，不必靠理解）**：
> 把被验证量从「未生效值」换成「生效值」，若那条 `OK` **一个字都不变** ⇒ 它是空判据。
> （等价说法：**它能否被「失败输入」打成失败？打不成即空。** —— 这与"门禁必须先做故意的失败测试"是同一原则的两个作用面：一个针对"门"，一个针对"OK 语句"。）

**阈值判据的通则**：
> 判据必须能取到「**非预期值**」；**取不到的阈值只是装饰**。
> （A vs B **差值** = 至少两个读数；**单边阈值** = 一个读数 **加一个假设**。`>0` / `>=0` / `!= NULL` 这类在"什么都没装"时同样成立。）
> 实例：某加固的逃生门判据写 `(>0 ⇒ 有效)`，而实测 A=10、B=10（**两数相等**）却照样宣布"有效"。

## 九、★ 文档变更的「证明方式」取决于变更类型

**任何文档变更都要先声明它属于哪一类，并给出对应的证明。不能自证的变更一律禁止。**

| 操作 | 证明方式 |
|---|---|
| **纯 append**（尾部追加） | `head -旧行数 新文件 \| md5sum` == 旧 md5（机械可核验） |
| **受控原位改写**（授权、唯一写入者） | **`diff` = 恰好 N 行、行数不变** ＋ 前置断言（待改的旧值在全表**只出现 1 次**，防行号错位） |
| **静默插行**（未授权） | **无法自证** ⇒ **禁止**；只能靠事后比对旧快照发现 |

配套：**活文档不进 md5 冻结基线**（改冻"条目标题集合"）；**登记表是承诺账本，口径变了就另加一行、不原地改历史**。

**「受控原位改写」的五条必查**（缺一不可）：
1. **`diff` = 恰好 N 行**、**行数不变**；
2. ★ **行错位检查**：确认 diff 里**只有目标行**。
   —— 因为「**别处没被动过**」是一个**关于变化的事实**，而**现盘里没有"之前"** ⇒ **"看现盘"在原理上无法回答它**，只有 `diff 改前 vs 改后` 能给出这个新事实。
   （这一步是"改细节"时最易漏、后果最重的一类：改了别处而在别处碰巧对上时，肉眼完全看不出来。）
3. **全表同 token 的去向交代**：把所有含该 token 的行**逐一归属**（正当用法 ／ 目标行 ／ 订正注记）⇒ 能说「**不存在未标注的该 token**」，才算「改对地方」的**完整**证明。
4. ★ **文件间范围**：操作后用 `find -newermt <操作前时点>`，**逐个归因命中项**。
   —— ★ **标准不是「只命中目标文件」**：在多主体并发环境下**原理上不可达**（别人随时在写盘），**会稳定产生假警报**。
   —— **正确标准是「每一个命中项都能归因到某个已知活动」；只有「无法归因的命中项」才是警报。**
   —— **文件内 `diff` 只能证「这个文件改了哪几行」，不能证「没改别的文件」**。
   ⇒ 与第 2、3 条同源：**『唯一』在多主体环境里几乎总会被打破；『可归因』才是可维持的标准**（token 计数如此，文件范围亦然）。
5. ★ **属性范围**（mode / owner / mtime）：改前改后各做一次 `find <dir> -printf '%m %p\n' | sort` 对比。
   —— **「内容对」≠「属性对」**，而**属性错从内容上看不出来**（`diff` / 内容比对 / 日志全都正常）。
   —— 实测事故：用 `mktemp`（默认 `600`）+ `mv` 做"原子写" ⇒ 目标文件**从 `664` 被静默降为 `600`（丢了组可读）**，**内容零变动、mtime 也正常**，**只有 mode 快照 diff 能看见**。
   ⇒ 处置：原子写后**显式 `chmod` 回目标应有权限**（或用 `install -m`）；**只比内容的人永远看不见它**。

**★★ 「不存在」的证明方式与「存在」完全不同**：

| 命题 | 需要什么 |
|---|---|
| **"存在"** | **一次命中**即可（一次 `ls` / 一次 `md5sum`） |
| **"不存在"** | ★ **穷举 + 逐个归属**（列出目录／集合的**全部内容**，逐个排除）。**不能靠关键词 grep** —— **因为关键词本身可能就是错的** |

实测教训：用 `find -iname '*gate*' -o -iname '*片段*'` 去找一个名为 `起跑器统一门禁_prologue_v1.sh` 的文件 ⇒ **零命中**，于是报"未出" —— 而文件**早已落盘**。
⇒ **讽刺点**：当事人**自己立的门禁规则里就有「零命中 ⇒ 必须失败」**，却在巡检实践里把"零命中"读成了"不存在"当结论。
⇒ 这是"**不要判定一个你没打开看过的东西**"的另一种载体：**"没匹配到"是匹配器的问题，不一定是被匹配物的问题。**

**前置断言的锚点**：锚**目标行的语义特征**（例 `` ^  - 产生上述数字的命令.*ss -tnp `` 的 `grep -c`），**不要锚"裸 token 全局唯一"** —— 后者在文档有合法引用时**必被打破**（结果要么恒过 = 空判据，要么误拦 = 干扰）。

**规则与实操不一致时**：**不要默认"实操错了"** —— 先判定哪个更合理，再改**代价低、且不扰动历史**的那一边。
（实测：某表的变更记录"**实操写文末随附块、规则说顶部表**" ⇒ 判定实操更合理 ⇒ **改规则措辞**，顶表旧行作为历史保留。）
⇒ 这条也呼应"**不要判定一个你没打开看过的东西**"：**不一致是一个需要判定的信号，不是一个"照规则纠偏"的指令。**

### 补充 2：★ `append` 的判据是「**旧内容是新内容的前缀**」，不是「行数变多」

- **append 的定义性质**：新内容以旧内容为**前缀** ⇒ 判据 = `head -<旧行数> 新 | md5sum` **== 旧 md5**。
- ★★ **这条必须写成脚本内的前置/后置断言，不能只当"事后留痕"**。实测教训：一次 append 的 python 写成
  `recs[:-1] + [row+E[91]]` ⇒ **把原最后一行替换掉了**，表现为 **`diff = NcN`（改，而不是 `NaM` 增）+ 行数守恒 + md5 变**。
  ★ **这个 bug 最毒之处恰恰是「行数守恒」** —— 而**"行数变多了"正是 append 操作里最容易让人放心的信号**：
  **替换 1 行 + 丢掉 1 行 = 行数不变** ⇒ 一切"看行数"的检查**全部通过**。
  它最终**只靠事后 `diff` 复核才发现** —— 因为当时没人把那条前缀性质**写成断言**。
- ⇒ 两条件一起用并**卡在写盘之前**：`新行数 == 旧行数 + 追加行数` **且** `head -旧行数 新 | md5sum == 旧 md5`；不满足即**不写**。
- ⇒ 同族通则：**能拦住"我写错了"的断言，才是资产。**

### 补充 3：★ 多目标写入必须**原子**；`diff` 的 hunk 头**不是插入位置的忠实记录**

**（a）多文件写入的原子性**
- 实测：一份脚本先改 A（md5 断言失败、**A 零改动**）→ 却**继续改了 B**（漏写 `rc` 守卫）⇒ 产出**跨文件不一致态**（A 未改、B 已改），而两边**看起来都"正常"**。
  ⇒ **"断言拦住了一半" 比 "完全没拦" 更坏**：完全没拦，至少状态是一致的、能被整批回滚。
- 两级方案，**取更强的那一级**：
  1. **下限**：逐步检 `rc`，前步失败即退出、不跑后步；
  2. ★★ **推荐（两阶段提交）**：所有目标先写 `.tmp` → **逐项校验** → **全部通过后统一 `os.replace`**；**任一失败 ⇒ 一个都不落**。
- **为什么"检 rc"不够**：它只能防"**前步失败**"，防不了"**后步失败、而前步已落盘**"。
- 与既有条目的关系：**单文件原子写 = 写 tmp → 校验 → replace**；**多文件 = 全部 tmp → 全部校验 → 全部 replace**。**同一条线。**

**（b）行号 / hunk 头必须**机器实测**回填**
- 实测：插入块的末行**逐字等于既有邻行** ⇒ `diff` 把重复行并入公共区 ⇒ **hunk 头整体前移一行**（人推 `595a597,603`，实测 `594a596,602`）。
  ⇒ **`diff` 的 hunk 头不是"你插在哪"的忠实记录** —— 它会因重复行而漂。
- 三条做法：① **插入 / 留痕行必须唯一化**（不与邻行逐字相同）；② **hunk 头与一切行号必须机器实测回填**，不得人推硬编码；③ 引用 hunk 头前先实测。
- 归族：这是"**数字须附产生命令**"的扩展 —— **行号与 hunk 头也是"数字"**。
- ★★ 补充：**「hunk 数」≠「改动行数」，而且主判据必须用「改动行数」**。
  实测：三行**连续**改动被 `diff` 并为**一个** hunk（`107,109c108,110`）⇒ **hunk 数 = 4、改动行数 = 5**。
  ⇒ 因此"`diff` **恰好 N 处**"是一句**含糊**的要求（N 到底是 hunk 数还是行数？）—— 我下过整整一段时间的这种指令，**受令方只能猜**，猜错还要背锅。
  ⇒ 统一写法：**「改动行数：删 X 增 Y；hunk 数 Z（供参考）」**，**主判据一律用「改动行数」**；hunk 头只用来定位。
  ⇒ 教训：**下指令时的"数"必须先自我消歧** —— 否则手推必然出错，而**错在指令、不在执行**。

### 补充：**原位插入的判据是「双向锚定」，不是「diff 几行」**

- `diff` 只回答"**有几行不同**"，它**不回答"别处有没有被动过"**。在原位插入（文件中间增/删行）场景必须另做**双向锚定**：
  - `head -<改动点前> 新 | md5sum` == `head -<同数> 旧 | md5sum` ⇒ **前段**未被扰动
  - `tail -n +<改动点后> 新 | md5sum` == `tail -n +<原改动点后> 旧 | md5sum` ⇒ **后段**未被扰动
  - 两侧都相等 ⇒ **除目标那一行外逐字节一致**（实测：`c3cefa0d…` / `54eb8973…` 两侧各命中）
- 注意：**"行数守恒"在插入场景下不成立**（插入必然增行）⇒ 此时"守恒"的对象是**除目标行外的全部内容**，由双向锚定来证。
- 对比：纯 append 场景有更强的单命令判据 —— **`head -<旧行数> 新 | md5sum` == 旧 md5**。

### 补充 4：★★ 「量法」必须显式声明 —— **两个错误相消会伪造一次"验证通过"**

**事故（实测）**：我向执行方下达验收要求「报新 md5 + **行数 233**」。执行方量出 **232**（`wc -l`）。
**真基准是 231** —— 我的 233 来自一份**转述摘要里陈旧的"232 行"**。
⇒ **我错（该报 232）+ 基准错（真值 231）+ 双方数字看起来吻合** ⇒ 生成了一个**谁都没有真查过的"验证通过"**。
⇒ ★ 这比"两个人量出不同的数"危险得多：**不同的数会触发排查；相同的错数会直接放行。**

**根因：「行数」这个词没有唯一含义。**

| 量法 | 结果（以换行结尾、n 行文件） |
|---|---|
| `wc -l` | **n**（数换行符） |
| `awk 'END{print NR}'` | **n**（若末行无换行则 +1） |
| Python `len(text.split('\n'))` | **n + 1**（末尾多一个空元素） |

⇒ 两种主流量法**恒定差 1**。一旦上下游混用，**这个 ±1 的偏置会被静默吸收**，任何"差不多对上了"的核对都会通过。

**规则**
1. **报任何"数"时必须写明量法**（`wc -l` / `wc -c` / `split` / `awk END{NR}`）。**量法一变，数就变** —— 不写量法的数不可核对。
2. **基准值不得引用转述**（摘要、转述稿、他人的消息、上一轮的结论）。基准必须**当场实测**，并同时记录它的 md5 **与量法**。
3. ★★ **两个独立来源给出同一个数，不构成验证。** 只有当两者**量法相同且基准同源**时才算验证；否则"吻合"可能只是**同一个错误被复述了两次**，或**两个反向错误互相抵消**。
4. **交叉验证的正确形态是「换量法」**（`wc -l` ↔ `awk END{NR}` ↔ 逐行解析计数），**不是"换个人用同一量法再问一遍"**。
5. 派工时的写法：不写「报行数 N」，而写「报行数（`wc -l`）+ 与基准的差值」。

**归族**：这是"**数字须附产生命令**"的加强版 —— **数字须附「产生它的命令 + 量法」**。
**同族通则**：**当"两个来源都对上了"时，先问一句"它们是不是用同一种方式量的、对的是不是同一个基准"。**

### 补充 5：★★ 「改前 → 改后」的基准必须**逐项求和**，不得心算（2026-09-24 实测，与补充 4 同型）

**事故（实测）**：我（team-lead）向执行方下达同步要求：「《交付总览》L140 `136 行` → **`137 行`**」。
**真值是 139** —— 我**只算了 §四 的 1 行**（尾插 1 事件行），**漏计了 §三 的 2 行**（第 18 条 1 行 + 元规则 1 行）：
`136` **+ 2（§三）** **+ 1（§四）** = **139**。
执行方按实际落 **139**，并把 L140 同批改为 `139 行`，同时**把我的推导错误原样列出来**（`136+2+1`）让我复核。
⇒ **我没查就被推翻，而且推翻得对。**

**与补充 4 的关系：同型复发。**
- 补充 4：「基准数**抄自转述**」（引用了一个陈旧的值）
- 补充 5：「基准数**由心算得出**」（只数了自己当场想起来的那一项）
- **共同点：错误都在"基准的推导"环节，且两端的数看起来都"像是那么回事"，因此不会触发任何排查。**
- ⚠ **这是同一类错误的第二次**：**凡是"由人脑推导出的基准数"，都必须能被机器复算。**

**规则**
1. 「改前 → 改后」的推导，必须写成**显式求和式**，且**每一项都指名**（哪个文件 / 哪一处 / 净增几行）：
   `改后 = 改前 + Σ(各变更项净增)`。
   ❌ 禁写：「约 137」「加了几行，大概 137」——**没有求和式的行数就是转述**。
2. **交叉校验必须用 `diff` 的 `add − del`**：净增 == `(add 行数) − (del 行数)`。
   本次：`4 add − 1 del = +3` ⇒ `136 + 3 = 139` ✓ **两路独立得出同一个数**（这才是真验证，见补充 4 第 3 条）。
3. **「净增 0」的变更项要显式标出来**，否则它要么被误加、要么被整项漏掉。
   本次：`标题整格重写` = `1 del + 1 add` = **净增 0**（不参与求和，但必须出现在清单里）。
4. **多文件时逐文件各算一次，不得合并心算**（本次台账 +3 行、总览 +0 行，是两个不同的数）。
5. ★ **元规则 —— 权威让位于可复算**：当执行方回报的数与我的基准不符时，**裁决依据是"谁的推导能被机器复算"，不是"谁的层级高"**。
   我要求执行方附可复算的求和式；**我必须给我的基准也附可复算的求和式** —— 单向要求等于把同一类错误留在指挥链上游。

**归族**：与补充 4 合起来是一条 —— **凡"数"，须能回答三个问题：① 怎么量的（量法）② 跟谁比（基准，同源）③ 怎么算出来的（求和式）。**
**同族通则（反向）**：**当下属的数与我的数不符时，先按"谁可复算"判，而不是先按"谁该对"判。**

### 补充 6：★ 读 `diff` 时，**「没被列出的行」＝「相同」**，不是「不存在」（2026-09-24 实测）

**事故**：我生成两个版本的 `difflib.unified_diff`，看到「图 7」节只列了 1 行差异，就向下游报告「该节『★ 机制与画法』段**整段缺失**」。**实际那一段在两个版本里逐字相同 —— 因为相同，所以没被列出来。** 下游用程序逐节比对后把我驳回，**驳回得对**。

**判据**
1. **`diff` 的语义是「只报差异」。** 输出里没有的东西，**不构成"它不存在"的证据**。
2. **要断言"X 缺失"，必须回载体 `grep X`**，不能看自己的工具输出。
3. 读 diff 的正确姿势：**先看它报了几处差异，再问"还有多少行是相同的"** —— 两者之和应等于总行数。**只读 `-`/`+` 是抽样，不是全集。**

**同族**：这是「检索形态不匹配 ⇒ 假否定」家族的**第 9 个变体**，且是**最隐蔽的一个** ——
前面 8 个都是「我的**检索方式**不对」；**这一个是我检索对了、却把**我自己的输出**当成了全集**。

**反向自保**：**凡"缺失 / 没有 / 少了一段"类结论，判据一律是"回载体里查"，永远不是"我的输出里没看到"。**

**另一条同批教训**：**「报告发了、产物又改了」与「产物改了、报告没跟上」是同一枚硬币的两面** ——
- 前者（下游）：回报里的 md5 必须是**最后一次写盘后**的；
- 后者（执行方）：**改完再报，或明确写"以后一次为准"**。
两者都会导致**主事者每次都必须重新扫盘才能对上账**，等于把核验成本转嫁给了本已最忙的一环。

### ★★ 同名指令冲突：**三条判据，不看"哪封更晚"**（2026-09-24 实测，有直接证词）

**背景**：本环境下**同一角色可能有多个唤醒实例**（每次唤醒是新实例、不继承上一轮完整上下文），且**可能存在另一个会话的 lead 在给同一批执行者下指令**。

**实测**：某执行者**同时收到两封署名 "team-lead"、内容冲突的信** ——
- 一封的判据**可满足**（`产物 hex ⊆（色卡 ∪ 结构默认色）`）
- 另一封的判据**在事实上不可满足**（`产物 hex − 色卡全集 = ∅`，而源里已引入一个色卡外的值）

**它没有按"较晚到"选，而是按三条选**（这三条由 team-lead 正式收编为规则）：

> ① **哪一封能落成契约条款**（有据可查）
> ② **哪一封在事实上可满足**（不要求破坏另一条硬约束）
> ③ **哪一封有本会话 lead 的、可对盘的落盘痕迹**
>
> **三条同指一封 ⇒ 按它执行 + 原样报告冲突。三条不一致 ⇒ 停手报告，不许自己选。**

**⇒ 这是"两套指令并行"局面下唯一可用的防身术。**

### ★★ 并发自证的唯一可靠方法：**用"工具调用记录"逐条对表**（实测）

> **保存"我创建过什么"的清单（创建时刻 + 文件名），事后逐条对表。**
> **判据：在盘某文件的创建时刻，本会话的上下文里有没有对应的创建调用。**

| 对表结果 | 结论 | 反面（不这么做会怎样） |
|---|---|---|
| **有**创建调用 | **是我建的** | 会因"我不记得"而判成外人 ⇒ **"自产当外人"** |
| **无**创建调用 | **可能是同角色的其它唤醒轮次** | 会硬断定"第三方入侵" ⇒ **过度归因** |
| **分不开** | **就说分不开，不臆断** | 硬分一个 = **猜** |

**实例**：某执行者先报"存在并行写者活动"，后用此法**把自己的 15 件产物认了回来**（含它当作"铁证"的那一刻），并**主动撤回**该结论、把证据收敛到"经得起复核的那一半"。**"我从没错过"没有价值；"我撤掉自己刚立的论点"才有。**

**根因与对策**
- 根因：**每次唤醒是新实例、不继承上一轮完整上下文** ⇒ 执行者**无法可靠区分"谁在什么时候说过什么"**。这一整轮"张冠李戴"共四向：**把别人的话赖给对方 / 把自己的错揽给自己 / 把自己的产出当外人 / 把对方的话当外人**。
- 对策①：**一切交付凭据必须是"能对盘的客观量"**（md5 / 内容指纹 / `文件名|字节|行数|md5|mtime` 四元组），**不是记忆、不是"已完成"**。
- 对策②：**上游任何变动，先复算客观量、再上报，不跟动。**
- 对策③：**写前声明意图、写后核对指纹**（`_WRITE_INTENT.md` / `_WRITE_DONE.md`）：**冲突判据 = 实际指纹 ≠ 目标指纹 ⇒ 有另一实例在写同一批**。此判据**不依赖"谁在写"，只看"写出来的对不对"**，是并发下唯一稳定的判据。

### ★ 「判据过窄」—— 拿"有没有我说过那句话"当判据（2026-09-24，我自己的错）

**事故**：我要求执行方把某份记录里的一句话改成我指定的表述。核验时**我用"含不含我指定那句话"去查**，得 `False`，于是判定"它没改"。
**实际**：它把**整个判据的口径换掉了**（从"md5 快照互证"改成"md5 不适用、改用内容指纹"），并**把原因写进去了** —— **比我要求的更彻底。**

**⇒ 目标从来不是"有没有我说过那句话"，而是"那段内容对不对"。**

**判据（补）**
1. **核验改动时，判据要落在"目标性质"上，不落在"我指定的字面"上。**
2. **允许执行方用比我的要求更好的写法达到同一目的** —— 我的字面要求只是**一种实现**，不是标准答案。
3. **发现"它没按我说的改、但结果对"时，先问"是不是我的判据窄了"，再问"它是不是没改"。**

**同族**：这是「检索形态假否定」家族的又一变体 —— **前八次是检索方式错，第九次是把自己的输出当全集，这一（第十）次是"把指定字面当标准"。**

### ★ 「检索形态假否定」本族变体清单（截至 2026-09-24，**共 11 例**）

| # | 形态 | 后果 |
|---|---|---|
| 1 | `grep "\*\*…\*\*"` —— 把 Markdown 强调符当正文 | 假否 |
| 2 | `ls \| grep` 多行污染 | 假否 |
| 3 | `cut -c` 按**字节**切多字节字符 | 显示乱码（**文件无损**，差点误判"文件坏了"） |
| 4 | 正则写死**双引号**，漏**单引号**（`viewBox='…'`，svglite 用单引号） | 假否 |
| 5 | **全角空格 `U+3000`** 未处理 | 假否 |
| 6 | `export PATH` 写在 `diff` **之后**（当时 shell 未就绪） | 假否 |
| 7 | 四位小数正则漏两/三位小数值 | 假否 |
| 8 | 探针串与目标的实际形态不匹配 | 假否 |
| 9 | **读 `diff` 只读 `-`/`+` 行，未核「未列出＝相同」** | **假否（误判"缺整段"）** |
| 10 | **拿"有没有我指定那句话"当判据** | **假否（判据过窄）** |
| 11 | **`text.lower()` 之后用驼峰正则查 `viewBox`** | **假否（大小写被自己抹掉）** |

**共同点**：**都是「我的检索/判据形态」与「载体的实际形态」不匹配，而我把「我的输出里没有」当成了「载体里没有」。**

**唯一解药**：
> **凡「我没找到 / 缺失 / 没有 / 少了一段」类结论 —— 必须回载体复核，且用两种以上形态；或直接"程序枚举其全集、再取补集"。**

**⇒ 这也是「补集式扫描优于清单式扫描」的根据**：清单由人的记性决定，**补集由机器的枚举决定**。

### ★★ 「指向」要改，「记录」要留 —— 批改引用时必须先分这两类（2026-09-24 实测）

**场景**：某脚本被退休（移入 `_retired/`）后，全库 `grep` 它的名字，会命中**两类完全相反的东西**：

| 类 | 长什么样 | 处置 |
|---|---|---|
| **指向** | **存活脚本的 docstring / 注释 / runner 说明 / 契约 / 图注** —— 读者**照它去找**那个已退休的件 | **改**（否则读者照着走会走空） |
| **记录** | **溯源日志 / 迁移清单 / 变更留痕 / `_retired/README.md`** —— 它记录的是"**这件事发生过**" | **留**（改了 = **伪造"此件从未存在过"**） |

**判据一句话**：
> **该处在读者路径上「指向」它 ⇒ 改；只是「记录」它曾被移走 ⇒ 留。**

**⚠ 操作陷阱**：**`grep` 命中 ≠ 该改。** 必须先按**路径与语境二次筛**，否则会把溯源日志一起改掉。
⇒ 这与本族其它错误同源：**把"我的检索命中了它"直接当成"它该被处理"** —— 而**命中只是"出现了这个名字"，不是"这里需要修正"**。

**附带产出**：修完之后，判"清干净了没有"的**判据不能是"我 grep 还有没有命中"**（因为"记录"类**应当继续命中**），而应是：
> **存活脚本的 docstring/注释/runner 说明/契约/图注里，指向已退休件的引用 = 0 处。**

## ★★ 收到一封指令时，先分流它属于哪一类（2026-09-24 实测，执行方自订）

> **状态性指令 → 带 md5 的锚点**
> **判据性指令 → 已落盘的契约条款**
> **两者都无 → 停下来问**

**为什么比"三条判据"更根本**：「三条判据」解决的是**两封冲突时选哪封**；**这条解决的是"收到一封时先看什么"** —— 它是**入口处**的纪律。

**用法**：
- 说「已冻结 / 放行 / 停手 / 可以动了」的 ⇒ **去看锚点文件的 md5，不看信**；
- 说「判据应该是 X」的 ⇒ **去看契约里有没有这条，不看信**；
- **两者都查不到 ⇒ 停下来问**，不要凭"这封像是最新的"执行。

**配套的反面清单**（这些都**不算**依据）：
- ❌ "这封更晚到"
- ❌ "这封语气更像正式指令"
- ❌ "上次那封是这么说的"
- ✅ 只有两样：**可复算的锚点 md5** 与 **可引用的契约条款**

## 十、协作行为的两条通则

1. **当执行某条指令会违反一条已生效的纪律时**：**按纪律做，并写明"我偏离了字面指令、原因是它与 XX 纪律冲突"**。
   —— **不照办**（会破坏纪律）、**也不拒绝**（会阻塞任务），而是**校正 + 说明**。
2. **同一处纠正必须在所有线上同步落实**；且**"只此一例"这种结论要证，不要猜**（用一次全仓库 `grep` 把它证掉）。
3. **★ 独立复算不是"核对对方给的数字"，而是"给自己一次发现的机会"。**
   > **转述只能给「一致 / 不一致」；复算才给「发现」。**
   —— 实测：某人本意只是核对一个日志 token 的**位置**，重跑时发现两版日志里同一个 token 对应 `connect=10` 与 `connect=0`（**token 相同、结论相反**），由此发现一整种失效形态。
   ⇒ 所以把"要求复算"写成**理由句**，而不是命令句。
4. **转述数字必须附「产生它的命令 + 时点 + 口径」**（口径含 `grep` 目标、计数对象、是否含表头等）。
   —— 实测教训：一个行数在转述后变成 **899**，逐一试过四种计数口径（678 / 681 / 1473 / 1423）**无一可复现**（真值 **30**）；另一处 33 实为 22（混入了"全天数"）。
   ⇒ **数字一旦离开产生它的命令，就退化成"记忆值"，而记忆值会漂。**
   ⇒ 推论：**「命令栏」本身也必须可被复核，否则它只是另一种记忆值**（实测：某条目的命令栏写 `ss -tnp`，而源码里是 `strace -f -e trace=connect`）。
6. ★ **复核一个数字时，要连它的「适用范围(scope)」一起复核** —— 数字对、scope 错，等于数字错。
   —— 实测：我把某文档里一句「**A 档 19 条中…4 条单工具**」当成 A 档事实写进了任务指令；而**同一份文档上一小节自己声明预检对象是「32 个候选」** ⇒
   **同一文档内 scope 自相矛盾**，那 4 条里有 3 条其实属于 B 档、根本不在 A 档成员集（A 档实测 = 可分析 13 / 单工具 1 / 无候选 5）。
   ⇒ 后果不只是数字错：**下游会去找 3 条不存在的成员**（正是"让人去查一条不存在的问题"那一类）。
   ⇒ 做法：**摘录数字时，顺手把给出它的那句上下文一起摘下来**；若同一文档里两个 scope 打架，**以被明确声明过的那个为准，并把矛盾点上报**，不要替它圆场。
5. **"看" 与 "跑" 是互补的两条**：**看，是为了不误判；跑，是为了有发现。**

### ★ 盘面未变 ≠ 执行方未做：先问「指令是否送达」

- **症状不可区分**：**「投递丢失」与「指令已达但未执行」在盘面上完全同形** —— 都是"文件没变"。
  ⇒ **"文件没变"只能推出「某事没发生」，推不出「是执行方没做」。**
- 实测：一次"收到完成通知、但无回报内容 + 盘面 md5 一字未变" ⇒ 我判为"**他没落地**"，
  实际是**他从未收到那份裁定**（消息投递丢失；我读到的"未变"其实是**上一批的终态**）。
- ⇒ 通则：**盘面未变时，先问"指令是否送达"，再判断"是否执行"**；
  并且**措辞上不要把归因预设成对方的问题**（催问要对，定性要晚）。
- ★★ 配套（本项目用血换来的）：**如果一类故障反复发生（如"裁定未送达"），就必须把该通道换成可恢复的载体。**
  ⇒ **凡"我已下、尚未见回报"的裁定，必须在共享台账里有一行**（即"在飞行中的裁定必须可恢复"）；
  ⇒ **只走消息的裁定，视为未送达。**
  —— 反面教材：某个项目**明明已经为"消息丢失"专门建了台账**，负责人却**继续用消息发裁定**，
  等于**把防丢失机制搁在一边、继续用那个会丢的通道**。
- 推论：**"问而不判"是对的，但问句的开头不要先下结论** —— 否则对方要先花力气反驳你的归因，才轮到说事实。

### ★ 在不可靠通道上，永远不要写「见上一条」—— 每次自包含

- 实测：同一项目一个会话内**投递丢失 3 次**，其中包括「**同一条消息只到了一半**」（前半段到了、后半段没到）。
  ⇒ 在这种通道上，**「见上一条 / 见上文 / 如上」= 没写**。
- ⇒ 通则：**每次发言自包含** —— **把要点全文内联**（哪怕是追问、哪怕与上一条重复）。
- ★ **一次实测的"救回"**：把「验收结论 + 新派工」混排成一条时，**只到了验收那段**；
  但因为**把新派工的要点全文内联在那条里**（而不是写"见上文"），接收方**据此照录无误、代价 = 0 轮往返**。
  ⇒ 所以：**混排可以，但每一段必须自包含**（更稳的做法是**干脆分条发**）。
- ★ 配套（已验）：**决定性约定不要只走消息** ——
  **"我已下、尚未见回报"的裁定必须在共享台账里有一行**；**只走消息的裁定，视为未送达**。
- ⇒ 推论：**故障频率决定通道选择** —— 同一类丢失反复出现（≥3 次）时，**必须换载体**，
  而不是"下次小心点"。**可靠性问题不会因为更谨慎而消失，只会因为换载体而消失。**

### ★★ 「投递丢失」是需要证据的断言 —— 单方一句"我没收到"不足以定案

- 实测：一方报「**没收到那半段** ⇒ 确认第 3 次投递丢失」，**我据此向老板报了"丢失"**；
  随后该方**改口**：「那半段**我收到了**（不是只到一半）」 ⇒ **两条说法互相矛盾**。
- ⇒ 判定"丢失"至少需要：① **发送记录**；② 对方**明确指出缺的是哪一段**；
  ③ 若事后对方又说收到 ⇒ **改记为「延迟送达」**，并**更正已发布的结论**。
- ⇒ 这与「**盘面未变 ≠ 执行方未做**」严格同族：**症状相同，归因必须另有证据**。
  而它**更进一步**：**归因一经发布，修改它也要走同样的流程** ——
  **对外说过的判断，不能私下改掉，必须明确更正。**
- ⇒ 措辞纪律：**未定案前，把它写成"待核"而不是"已确认"**；**"第 N 次"这类计数尤其要谨慎**
  （计数会进汇报、会被引用，错一次要更正两处）。

### ★★ 归因要准 —— 既不做「预设对方有错」，也不做「和气式全揽」

**★ 2026-09-24 双向实例（同一条纪律的两个方向，本会话同一批人上先后出现）**

- **方向一（预设对方有错）**：执行方把自己上一条报告里写过的判断，事后归给 lead（原文写「**你**差异表里说…」），而 lead 那封里根本没有这句。
- **方向二（和气式全揽）**：**同一个执行方在下一轮反转**，主动把那句揽到自己身上（「这句是我自己写的，我却把它归到了你头上」）——
  **而核查双方原件表明：那句确系 lead 所写** ⇒ **它把自己没犯的错认成了自己的**。
- ★★ **它自己引用了本纪律的原文**（「既不做预设对方有错，**也不做和气式全揽**」），**然后正在违反后半句** ⇒
  **引用纪律 ≠ 遵守纪律。** 能背出条款，不代表正在执行条款。
- ★★ **两个方向等价**：把别人的话赖给对方、把别人的错揽给自己，**是同一种失真** ——
  都会让将来的查账人看见一个**不存在的错**，并把整改力气花在不存在的地方。

**判据（照此裁，不凭印象）**
1. **归因的唯一依据是「原文在哪一方」** —— 把双方的消息/产物原文翻出来对照，**不靠记忆、不靠印象**。
2. **不要为了显得公允而多认。** 主动认领不属于自己的责任，**不是谦让，是制造假账**。
3. **发现归因翻转时，先问「是查了原文，还是只凭感觉」** —— 本实例里两次翻转都是**没查原文**造成的。
4. ★★ **把"来源断言回扫"当作交付前的固定检查项**（2026-09-24 实测，执行方自行发明）——
   **在交付前，把自己本批所有回报里每一条「来源断言」**（"这是谁给我的"「这是谁说的」「这依据谁的口径」）**逐条回扫、核对实情**。
   - 实测收益：某批三条来源断言，**查出 1 条失真**（把自出的方法论记成别人给的），**另 2 条经核无误**。
   - **为什么比"出事了再纠正"强**：它是**事前**的、**穷尽**的（覆盖本批每一条来源断言），而不是**事后**的、**碰到才查**的。
   - **两个方向都要扫**：
     - 把**别人的**记成自己的 / 记成第三方的 ⇒ 是**赖账**
     - 把**自己的**记成别人的 ⇒ 是**送走自己的方法论**（且会让后来人以为这条判断有外部背书）
   - **⇒ 功劳归错人与错误归错人，同为失真。**

- **两侧其实是同一类错**：**归因不是"按证据分责"，而是"按立场分责"**。
  实测（**同一件事的两次归因，两次都不准**）：
  ① 我先说「对方没收到 ⇒ **投递丢失**」 ⇒ **预设对方有错**；
  ② 对方随后把自己归成「**责任全在我这一侧**」 ⇒ **和气式全揽**。
  真相：**漏读（对方）＋ 混排且要点后置（我方）** ⇒ **两方各半**。
- ⇒ 通则：**按证据分责** —— **分责结论本身也必须能被证据支撑**（与"归因需证据"是同一条）。
- ⇒ 操作顺序：**先列证据 → 再定责**；**先问"我这边有什么可改进"→ 再问"对方漏了什么"**。
  ★ 注意：**"先自省"不等于"自揽"** —— 自省的目的是把责任划准，不是把责任领走。
- ★ 配套（已验）：**汇报里的"次数 / 计数"尤其脆弱** —— 一次不准的归因会**进汇报、被引用**，
  错一次要更正**两处**。
  ⇒ **未定案的数字，宁可写"待核"，也不要写成一个具体数。**
- ★★ **配套：计数规则必须对「自己方的数字」同样生效** —— 否则规则只对外、不向内。
  实测：一条**不可核实的计数**被写进了**制度文件的"立文理由"**里（"本轮发生 N 次 X"）⇒ 它会**变成"制度性事实"**，后人一律当它真。
  ⇒ 做法：**凡"计数"进制度 / 说明类文本，必须标注来源与验证状态**（如「**自述 · 未验证**」）。
- ★ **另一处手法：「一个计数」要按「它出现的载体类型」分层处理，不要一刀切**：
  **说明 / 体例行 ⇒ 必须标注**（它是**常设叙述**，会被反复引用）；
  **事件行（自带时点）⇒ 忠实保留、不动**（它记录的是"当时某人如此陈述"这一**事实**，本身是真的）。
  —— 这仍是「**状态 vs 事件**」那条区分在"计数"上的应用。
- ★★ **对"上级 / 己方来源"的数字照样按规则质疑，不构成越权。**
  这比执行一条命令难得多，**而它才是规则真正生效的标志**。

### ★★ 「派出去的活」必须有在飞清单 —— "没有回报"本身是一个必须被接住的信号

- 实测：一个会话里**两条派工静默了约 5 小时**无人察觉（一条要产出交付文档、一条要改权威口径文档）。
  根因：**负责人把注意力投到另一条线上之后，靠"记忆"跟踪派工** ⇒ **忘了自己派过什么**。
  ★ 更糟的是：**我在中途向上汇报"只剩一件在途"—— 报少了**（把两条报成一条）。
- ⇒ 通则：**凡"我派出去的活"，必须在盘面上有一张可盘点的「在飞清单」**
  （**派给谁 / 何时 / 要求什么 / 是否已回报**）；**每一次"现状汇报"之前，先盘这张表**。
- ★★ **"没有回报"不是"没有消息"，而是一个明确的异常信号** —— 必须有人定期去接。
  ⇒ 判别法：**同一批里，有的受派方逐条主动回报、有的全程沉默 ⇒ 沉默的那些就是风险点。**
- ⇒ 与「**裁定落台账**」是同一条，只是把范围从「**裁定**」扩到「**派工**」：
  **决定要落盘、派工要落盘、在飞要可盘点。**
- ⇒ 配套动作：**重派时一律"自包含"**（把要求全文内联，不写"见上一条"），并**要求开工前回执** ——
  在不可靠通道上，**回执是唯一可验证的"送达"证据**。

### ★★ 「过期的限制令」比「从没下过令」更糟 —— 限制令必须带解除条件，解除必须显式广播

- 实测：某条「**全局停手**」令（起因：**老板要断电**）的**前提早已消失** —— 服务器已重启，
  且**已在上面跑完大量作业**；但**执行方上下文里那条令还挂着** ⇒ 它**主动把一条本可正常做的工作也判成"受限"**，
  还专门来问"要不要停笔"。
- ⇒ 通则：**全局性限制令必须写明「解除条件」，且解除时必须「显式广播」**。
  **不能让执行方自己去判断"这令是否还成立"** —— **它看不到全局状态，只能保守执行**。
- ⇒ 配套：**派工附带「有效期 / 前提条件」**（如"仅限断电窗口内"），到期即自动失效；
  **没有前提条件的限制令，会被永久执行。**
- ★ 另一处同族：**派工前先查"这件事是不是已经做完了"**。
  实测：我给一名队员重派了一条**早已由我代做完成**的任务（起因 = 原受派方沉默），对方**一直挂着等"恢复"**。
  ⇒ **「在飞清单」应当同时记录「已完成」** —— 否则同一件事会被派两次，或永远悬着。

## 十一、★ 成本估算的前置问题

- **在问"跑多久"之前，先问"能不能不跑"。**
  实测：一个看起来要"跑网格几小时"的子网格，因为**上游已把全部成员的中间结果算完**，改成"切片复用"后是**分钟级**；另一个"全量重跑"因为**等价性已有数学证明**而直接取消。
- **成本与规模远非线性**（实测：对数比 16×，时间比只 3.7×）⇒ 小规模任务有**大额固定开销**，不能从大任务线性外推。
- **瓶颈是单块机械盘时「核数 ≈ 倍数」是错的直觉**（实测 `B(8) ≈ 100 > B(17) ≈ 64 MB/s`）⇒ 加并发只改变分摊方式，不改变总供给。
- **先算读量，再选读法**；只需少量键一律「1 遍 + 流式过滤」。（实测四次被这条挡下：7.56 TB / 9.9 TB / 3.5 h / 2.02 TB。）
- ★ **分母必须与「工作单元」同源** —— 这是比"刻度不同"更隐蔽的一类：日志里并排两个计数，**取错了那个当分母**。
  实测：一条跑批日志同一行印着 `结局 335/1400（pairs=521）`，而该批**真实工作单元 = 335 结局 × 4 暴露 = 1,340 次调用**
  （脚本全篇只有 **1 处**调用点、pair 层**无**子集过滤）；`521` 其实是**上游 MR 的显著对数**。
  ⇒ 拿它当分母，进度会算成 **`610/521 = 117%`**（终态 >100%），而正确刻度是 `610/1,340 ≈ 45.5%`。
  ⇒ 通则：**凡日志里出现两个计数，逐个问"这是谁的数"**；进度/ETA 一律用**与成本同构的量**（I/O 型 ⇒ 字节），
  并**在产物 meta 里写明"真实工作单元数"**，让下一个人不必再推一遍。
- ⚠️ **`read_bytes` 只计物理盘读**，页缓存命中不计 ⇒ 以它算出的进度是**下界**、ETA 是**上界**（汇报时按这个方向说）。
- ⚠️ **但不要把"用字节刻度"教条化** —— 关键判据是**分母本身是否被验证过**：
  接上例，字节分母 `114 GiB` 是脚本作者**估的**（`335 × ~0.34 GB`），而**调用总数 1,340 是我读脚本实证的**
  （唯一调用点 + 无 pair 过滤 + 4 个暴露全部加载成功）⇒ **此时"调用刻度"反而比"字节刻度"更硬**，应以它给 ETA 上界。
  ⇒ 通则：**硬刻度 = 分母经实证的那一个**；两个刻度都给出后，**取"分母更硬"的那个定 ETA，另一个用来证"在推进"**。
  ⇒ 再补一层：两类计数都可能是**下界** —— 调用刻度会**低估**进度（合并后 SNP 不足的对直接 `return(NULL)`，不产生输出行，故已完成 ≥ 标记数）。

## 十二、★★ 「跟着产物走的东西，要让产物自己带」（2026-09-24 全天实测）

### 12.1 限定声明必须由**产出该产物的代码**生成，不能手工补
手工补进产物的限定块，会在下一次重跑时**静默消失** —— 比"没有限定"更危险，因为读者会以为已看过全部边界。
- 做法：限定块写成脚本里的**模板常量**；其中的清单（如"新旧榜差集 6 条"）**由脚本现场算**，不许硬编码 id。
- 验收：**重跑后产物应与当前 md5 逐字节一致**。不一致 ⇒ 块里仍有手写成分，改到一致。
- 防的是：一次重跑产出一份"看起来干净、限定蒸发"的文件。

### 12.2 同族的四个兄弟（同一道理，四种形态）
| 形态 | 正确做法 |
|---|---|
| 活文档写自身 md5 | **不写自指值**，md5 由外部清单持有 |
| 结论只在消息里 | **落盘成文件**，回报只给路径 + 一行摘要 |
| 半成品用正式文件名 | 先写 `.PARTIAL`，**完成才原子改名** |
| 并发写同一产物 | **抢锁**（拿不到就静默退出码 0）+ **启动登记行** |

**一句话**：凡是"应该跟着产物走的东西"，都让产物自己带，不要靠人记着补。

### 12.3 「重复劳动」与「独立复核」在产物上长得一样
区别只在于**有没有被记成证据**。两个独立实现输出**逐字节一致** ⇒ 这是交叉验证证据，**必须保留并在 README 标明**；删掉等于扔掉证据。
- 但要指定 canonical（谁改名、谁只读复核），否则下次又变成两个写入者。

### 12.4 ★ 用错判据会导出**假缺陷**
实测事故：报"6,384 条含 H 键躺在 `HarmonicBondForce` 且未约束"。
- 真相：`HBF` 条目 12,400 = **真实键 4,706 + 1–3（Urey–Bradley）对 7,694**；判据是 `HG11–HG12` 这类 **H···H 对**——**按构造不可能是键**；真实含 H 键 35,348 条**全部已约束**。
- ⇒ 通则：**「某个集合里有这个元素」≠「这个元素属于该集合」**。下否定性结论前先问**这个集合的定义是什么**，并抽查几条看它们**是不是真有该属性**。
- 且：被推翻的结论**保留在原文（删除线）+ 附推翻它的判据表**，比删掉有用——下一个人很容易再犯同一个误判。

### 12.5 ★ 全局量在局部位点上**没有判别力**
实测：用"4399 原子的全局 RMSD 仅 0.046 Å"论证"突变位点的侧链构象不受影响" —— **错**。局部差异被全原子平均掉了。
- ⇒ 要论证局部，就量局部：**该残基侧链的重原子 RMSD / χ1-χ3 二面角差 / 逐残基序列比对**。
- ⇒ 通则：**结论的作用域必须与度量的作用域同阶**；用全局统计量支撑局部结论 = 偷换作用域。

### 12.6 ★ 机制层结论必须等**对照实验**，不能用"像"来定
实测：同一条链上，我先后给出三个机制解释（"交付不可复现"→"协议依赖"→"前缀累积"），**三个都被实测推翻**，最后落到的准确说法是「同一次调用内各行相互影响、**机制未明**」。
- ⇒ 通则：正文里**只允许写实测事实与可操作规则**；机制放进"待检验"，并在正文显式标注"机制未明"。**未解的机制不许写成已解。**
- 配套：**口径不同 ≠ 来源不明**。历史数字要写清它来自哪个口径（力场/参数/padding），不要写"来源不明"——后者会让后人无法解释自己的历史。

### 12.7 ★★ 一个成员只允许**一个活动实例**；收到明确回报前**不重复派单**
实测：因重复派单，同一天出现**三对**重复实例，其中一次两个实例**互相 SIGTERM**、互相改名对方日志、覆盖对方产物。
- **根因在调度方**（重复派单），不在执行方。处置：
  1. **纪律层**：一个成员只允许一个活动实例；**未收到明确回报前不发新指令**；工作目录放 `.owner` 主属标记。
  2. **工程层**：即使双开也无害 —— 锁 + `.PARTIAL` + 原子改名 + 启动登记。
- 冲突裁定：**以「盘上事实」为准，不听任何一支的自述**（实测：两支对其是否落盘各持一说，实际是"已落盘"）。
- 副产品：重复实例有时会歪打正着做**独立复核**（本次两对都如此）⇒ 别急着杀正在跑的那一支，先看它产出的是不是互补证据。

### 12.8 ★★ 归因不能做**假二分**：「排除了我们两支」≠「必是另一支」
实测：某次共享文件被写入，执行方排除自己后写「**必为另一个（同名）实例**」——**实际是主理人写的**。
- ⇒ 可写者集合 = **所有持有写入通道的人**（主理人 / 各成员 / 任何持 ssh 者），**不是"我们这两支"**。
- ⇒ 归因三律：①**先穷举可写者集合**，再逐一排除；②**只写"能证实的"**，不能证实的写「未知」；③**过期的事实要重取**——曾准确写下的事实（如"team-lead 未编辑过任何文件"）会因后续事件失效，**沿用等于制造假证据**。
- ⇒ 反向纪律：**中性改名保留，但说明必须写对**。名字错了只是不好看；**说明错了是在制造假证据**。

### 12.9 ★ 共享目录要有**写入日志**（归属留痕），与"锁 / .OWNER"配套
三个机制各管一件事，缺一不可：
| 机制 | 管什么 |
|---|---|
| **锁**（flock / 原子 mkdir） | 防**并发**污染 |
| **`.OWNER`** 主属标记 | 标**目录归谁** |
| **`logs/write_log.tsv`**（append-only） | 管**每次写入的归属** |
写入日志每行：`ISO时间 | instance_uuid | pid | 文件 | 改前md5 | 改后md5`；`instance_uuid` 由脚本首次运行生成并**持久化**（不同 UUID = 不同实例）。**只 append、不设门禁**。
- 理由：同为一名成员的两个实例**同名、同 uid，从文件系统上不可区分** ⇒ 没有写入日志，任何归属争议都只能靠互相排除（而排除法会犯 12.8 的错）。
- 判据：**当"谁写的"需要靠推断而不是靠记录时，就说明缺这张日志。**
- ⚠️ **但它的边界必须写清，别让它名过其实**（实测：盘中**无** per-instance 稳定令牌 —— `SSH_CLIENT` 源端口每次调用都变，harness 的环境变量不过 ssh）⇒ **区分实例只能靠各支自愿 `export GAMMA_INSTANCE_UUID`**：
  | 能 | 不能 |
  |---|---|
  | 记录**写什么 / 何时 / 改前改后 md5**（不依赖署名，价值最大） | **自动区分实例** |
  | 在各支都署名时，暴露「**无人认领的写入**」 | **检测不署名的写入者**（非协作的重复实例不会来写日志） |
  ⇒ **它不是"防重复实例"的机制**；防重复靠「不重复派单 + 锁 + `.PARTIAL`」。**写日志只管归属留痕。**
